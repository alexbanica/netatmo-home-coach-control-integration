## Implementation decisions and boundaries

1. Keep all production edits in `src/infrastructure/netatmo/NetatmoClient.ts` and `src/infrastructure/netatmo/WebSession.ts`. Preserve application gateway/domain contracts, `AppFactory`, HTTP transport, OAuth client, scheduler, health, logger implementation, settings and dependencies.
2. Add a synchronous, read-only `WebSession.canAttemptLogin(): boolean` reporting whether the existing `#attempted` budget is unused. Reflect it as a required member of the adapter-local `WebSessionLike` contract, validating it at construction alongside existing required methods. It neither consumes nor resets a budget and exposes no token or credential. Concrete composition already passes WebSession, so no composition change is needed. The service is serial; do not introduce concurrent callers or a second budget owner.
3. Add one private cycle-level recovery-attempt flag to NetatmoClient, reset only by its existing `beginCycle`. WebSession remains authoritative for password-login attempts. Do not call `beginCycle` from recovery, change when `#attempted` is consumed, or reset it on invalidation/login failure.
4. Separate one token-verification attempt from the recovery decision inside the pre-write `#webToken` path. Use a private discriminated result or equivalently private control flow to keep the recoverable-verification signal separate from ordinary exceptions. Do not add an application-visible retry field or reinterpret generic errors as recovery instructions. Narrow parsed external JSON before accessing fields; retain the current explicit-invalid/expired-message matcher as a trigger, with numeric forbidden code 13 as a veto. Apply the SPEC's status/parse exclusions before matching: 429, 5xx, redirects, transport errors and malformed JSON never qualify. Numeric codes 2/3 alone are not triggers.
5. On a qualifying completed verification rejection, invalidate the token and clear NetatmoClient's verification cache even when no recovery budget remains. Check cancellation, the private recovery flag, and `canAttemptLogin` before starting recovery. Consume the recovery flag before starting login, then obtain the replacement token and verify once. A failed replacement verification still applies qualifying invalidation but cannot recurse. Authentication-acquisition errors are not themselves verification-recovery triggers. Preserve existing invalidation/failure behavior for nonqualifying verification failures; add no recovery for generic 403 or code 13.
6. Leave the calibration POST outside the recovery control flow. Its request, parsing, invalidation and outcome classifications are unchanged. After `#webToken` succeeds, explicitly check cancellation and run the existing `beforeWrite` freshness callback before the single possible POST. Preserve existing aborted/skipped handling. Do not wrap or re-invoke `calibrateRoom`, change its inputs, reread target status, repeat discovery, or emit a provisional failed mapping when pre-write recovery succeeds.
7. Propagate rate-limit errors, Retry-After values and cancellation without conversion that would prevent existing use-case halting. Do not catch a verification transport failure as expiry. Preserve headers, exact allowed hosts, redirect policy, timeouts, challenge handling, credential redaction and no-POST-replay behavior.
8. Emit `netatmo.web_auth.prewrite_recovery.started`, `.succeeded` and `.failed` through the adapter's existing nonthrowing DEBUG diagnostic helper. Fixed outcomes are respectively `started`, `succeeded`, `failed`; only existing safe error categories or HTTP/API codes may accompany failure. Started is emitted only after both budgets permit actual login; succeeded follows replacement verification. No extra fields, raw error messages or logger changes are needed. Existing stage logs cover cases where recovery is not started.
